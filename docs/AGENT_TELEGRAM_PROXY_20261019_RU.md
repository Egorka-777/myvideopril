# Telegram: подключение через прокси и автоматическая диагностика

Ветка разработки: `fix/telegram-proxy-wss-20261019` (слита в **`main`**).
Версия EXE / worker / runtime: **`2026-10-19-telegram-proxy-v4`**. См. также `AGENT_TELEGRAM_LOGIN_20261019_RU.md`, `AGENT_TELEGRAM_CONNECT_20261017_RU.md`.

## Что установлено по журналам

19 октября одна и та же сессия успешно выполнила `get_me` без прокси в 11:48 (+07:00). Позже подключения через назначенный прокси к DC4 по обычному TCP заканчивались `ConnectionError`, хотя туннель к Telegram Web проходил. Это подтверждает, что сессия отвечала в момент успешной проверки. Точную причину отказа у провайдера по этим журналам определить нельзя.

До исправления приложение использовало для импортированной сессии только TCP к IP сервера. Теперь сначала проверяется MTProto через WSS/TLS на официальном домене того же DC, затем при сетевой ошибке — TCP того же DC. Назначенный прокси, ключ и аккаунт сохраняются. Прямого подключения при назначенном прокси нет. При отозванной сессии, блокировке и FloodWait перебор маршрутов не продолжается.

WSS реализован по https://core.telegram.org/mtproto/transports: `/apiws`, подпротокол `binary`, TLS с проверкой сертификата, abridged framing и obfuscation из закреплённой Telethon. Это дополнительный совместимый транспорт, а не доказательство работоспособности конкретного прокси. На реальном ПК обязательна проверка ниже.

## Установка агентом

1. Закрыть VideoBatch. Сохранить прежний комплект приложения для отката. Не удалять `%LOCALAPPDATA%/VideoBatchDesktop/telegram`, `telegram.vault`, его резервные копии, TData, JSON или session.
2. Скачать артефакт **Telegram-Proxy-Update** из успешного **Telegram workspace** на SHA **`main`** / `SOURCE_COMMIT.txt`, либо `git pull origin main` + Release-сборка. Развернуть весь комплект в папку приложения: EXE, DLL, обе папки native WebView2, `tools/telegram`, `tools/uploader`, `TELEGRAM_PACKAGE.json`, `SOURCE_COMMIT.txt`. Не смешивать отдельные файлы разных сборок. `node_modules` и пользовательские данные не переносятся из CI.
3. В PowerShell выполнить из папки приложения:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\telegram\doctor.ps1 -AppRoot (Get-Location).Path -Repair
```

Ожидается `exit_code: 0`, проверки package/runtime = ready. Эта команда проверяет комплект, версии зависимостей, импорт WSS и marker. Она **не проверяет вход в аккаунт**, пока не указан AccountIndex.

`-Repair` восстанавливает закреплённые зависимости и marker; несовместимую среду Python переносит в `venv.previous-*`, создавая Python 3.11 x64. Учётные записи, исходные файлы и прокси не изменяются. Для создания среды должен быть установлен Python 3.11 x64, для установки пакетов нужен интернет. Неверный комплект EXE/скриптов автоматически не заменяется: нужно целиком установить правильный артефакт.

4. Открыть приложение → Telegram. У нужного аккаунта оставить уже назначенный прокси из Dolphin. Нажать **Диагностика**. Проверяется именно выделенный аккаунт / выделенные аккаунты. Повторный импорт по умолчанию не требуется.
5. После успеха — **Открыть Telegram**. Проверка `get_me` и вход в Web — отдельные шаги. Веб-вход может запросить облачный пароль 2FA: его вводит пользователь в официальном веб-клиенте. Зелёный прокси сам по себе не означает вход в аккаунт.
6. Журнал → **Открыть отчёт диагностики**. Отчёт: `%LOCALAPPDATA%/VideoBatchDesktop/telegram/diagnostics/doctor-latest.json`. Системный отчёт рядом: `doctor-system.json`. В них нет ключа сессии, API hash, номера телефона, имени и URL/пароля прокси. `slot` — номер внутри последней проверки, не Telegram ID.

Для проверки без интерфейса, под тем же пользователем Windows:

```powershell
# N — номер аккаунта в сохранённом списке (с 1), не порядковый номер
# после сортировки таблицы. Если порядок неизвестен, используйте UI.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\telegram\doctor.ps1 -AppRoot (Get-Location).Path -AccountIndex 1
```

Команда использует защищённое хранилище приложения и тот же worker. Не экспортировать vault в JSON, не передавать пароли аргументами команд и не печатать сырой stdout worker: события `connection`/`imported` содержат ключи для сохранения в vault.

## Как агенту действовать по результату

| Код / результат | Следующий шаг | Автоматическое исправление |
| --- | --- | --- |
| PackageManifestMissing, PackageVersionMismatch, PackageFileMissing, PackageFileChanged, ExeWorkerMismatch | Установить целиком правильный CI-артефакт. Проверить `SOURCE_COMMIT.txt`. | Нет: не склеивать версии вручную. |
| RuntimeNotReady, RuntimeMarkerStale | Закрыть приложение, выполнить doctor с `-Repair`, повторить проверку. | Зависимости / marker. |
| RuntimeRepairFailed, RuntimeRepairTimeout | Проверить Python 3.11 x64 и доступ к установке пакетов. | Не запускать аккаунты до успешного runtime smoke. |
| proxy_tunnel | Сверить протокол, адрес, порт и авторизацию с сохранённым прокси Dolphin. Проверить, разрешает ли провайдер доступ к Telegram. | Не менять пароль и не переключать аккаунт на другой IP. |
| tls_certificate, tls_or_websocket, websocket_upgrade, binary_protocol | Проверить дату/время Windows и доступ через этот прокси к `*.web.telegram.org:443`. | Не отключать проверку TLS. |
| TimeoutError, ConnectionError, network / check_route | Смотреть `attempts`: отдельно WSS и TCP. Один раз повторить диагностику после проверки сети. | Нет бесконечного цикла или прямого обхода прокси. |
| unauthorized / manual_login | Войти в официальный клиент, получить актуальную сессию и импортировать её. | Не повторять авторизацию по кругу. |
| flood_wait / wait | Дождаться срока, указанного Telegram. | Подключение при сохранённой активной паузе не выполняется. |
| blocked, deactivated / stop | Остановить задачи; проверить состояние в официальном клиенте. | Не менять аккаунты/прокси для обхода ограничения. |
| configuration / check_import | Проверить парный JSON и тип сессии. | Не смешивать API ID и hash разных источников. |
| ready + get_me | Telegram действительно ответил на запрос аккаунта. `transport` показывает wss/tcp. | Можно открыть веб-окно. |

Не объявлять прокси нерабочим только потому, что аккаунт не авторизовался. В интерфейсе теперь **Частичный доступ** означает сетевой результат, а состояние аккаунта показывается отдельно. Доступность туннеля / TLS / WSS не заменяет `get_me`.

## Приёмка

- Один и тот же сохранённый аккаунт и назначенный прокси: диагностика даёт отчёт с транспортом и понятным действием.
- Если WSS проходит, а TCP к IP нет — подключение всё равно может подтвердиться через WSS; искусственного запрета из предварительной проверки нет.
- При неверном пароле прокси нет прямого подключения, циклических попыток и ложного статуса «аккаунт заблокирован».
- На Stop worker завершается в пределах установленного срока; аккаунты и исходники остаются.
- CI проверяет настоящий локальный SOCKS5 → TLS → WebSocket → шифрованные пакеты Telethon, отказ неверному TLS/паролю, отмену, отчёты, восстановление marker, отказ смешанному комплекту, C# vault/worker и native WebView2 из готового пакета.

Реальные реквизиты прокси и файл сессии в эту доработку не передавались. CI использует только синтетические локальные фикстуры; реальный вход на ПК нужно подтвердить по `get_me`, затем по веб-окну.
