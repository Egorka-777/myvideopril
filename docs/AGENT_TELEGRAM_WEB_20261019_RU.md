# Telegram Web: QR и автоматический вход

Ветка: `fix/telegram-web-login-20261019`. База main: `0d25785ee2caba82794e6d8da163908c18466084`.
Комплект EXE / worker / runtime: `2026-10-19-telegram-web-v5`.

## Что показывает скриншот

Проверка сессии уже успешна: Telegram подтвердил аккаунт. Веб-клиент при этом остаётся на экране загрузки QR. Это разные соединения: проверка импортированной сессии не создаёт веб-сессию браузера.

Приложение использует официальный QR-вход: ждёт готовый QR, проверяет импортированную сессию, запрашивает свежий QR и подтверждает его через `auth.acceptLoginToken`. Вручную сканировать QR телефоном в этом сценарии не требуется. Облачный пароль 2FA при запросе вводит пользователь на официальной странице. Ключи в localStorage, поддельные cookies и обход 2FA не используются.

По одним скриншотам нельзя подтвердить точную сетевую причину отсутствующего QR. В коде исправлены подтверждённые недостатки: «Обновить» не сбрасывало состояние предыдущей попытки; пустой контейнер QR не отличался от готового; ошибки сетевых маршрутов веб-окна не попадали в отчёт. При зависшем индикаторе теперь выполняется одна перезагрузка с очисткой только дискового кеша; данные входа не очищаются.

Web A использует `zwsN.web.telegram.org` (см. официальный исходник `Ajaxy/telegram-tt`, `src/lib/gramjs/Utils.ts`), тогда как проверка сессии использует домен DC из публичного MTProto-протокола. Если прокси отказывает на первом имени, мост пробует официальный TLS-домен **того же DC** через **тот же прокси**. TLS/SNI браузера и проверка сертификата сохраняются. Между DC, прокси или аккаунтами переключения нет. Рабочий адрес запоминается только на время текущего веб-окна.

Источники: https://github.com/Ajaxy/telegram-tt/blob/master/src/components/auth/AuthQrCode.tsx , https://github.com/Ajaxy/telegram-tt/blob/master/src/lib/gramjs/Utils.ts , https://core.telegram.org/api/qr-login , https://core.telegram.org/mtproto/transports .

## Установка на ПК

1. Закрыть VideoBatch и его веб-окна. Сохранить предыдущий комплект приложения для отката. Не удалять `telegram.vault`, резервные копии, TData / JSON / session и `%LOCALAPPDATA%/VideoBatchDesktop/telegram/web`.
2. Скачать **Telegram-Web-Update** из успешного запуска **Telegram workspace** этой ветки. Обновить комплектом EXE, DLL, `runtimes`, `tools/telegram`, `tools/uploader`, `TELEGRAM_PACKAGE.json`, `SOURCE_COMMIT.txt`. Отдельный старый EXE со свежим worker не использовать.
3. Из папки приложения выполнить:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\telegram\doctor.ps1 -AppRoot (Get-Location).Path -Repair
```

Ожидается `exit_code=0`, package/runtime=ready и версия v5. Команда восстанавливает компоненты, не выполняя вход в аккаунты. Требуется Python 3.11 x64; установка зависимостей требует интернет.

4. Telegram → выбрать уже сохранённый аккаунт с прежним прокси → «Диагностика» → дождаться «Telegram подтвердил аккаунт» → «Открыть Telegram».
5. Дождаться готового QR: приложение должно подтвердить его автоматически. При запросе 2FA пользователь вводит пароль в веб-окне. Успех — главный экран чатов и сообщение «Telegram открыт». Зелёная строка аккаунта отдельно от этого не является подтверждением веб-входа.

## Автоматическая диагностика и следующие шаги

Отчёт веб-входа: `%LOCALAPPDATA%/VideoBatchDesktop/telegram/diagnostics/doctor-web-latest.json`. В разделе «Журнал» кнопка «Открыть отчёт диагностики» открывает самый свежий отчёт, включая веб-вход. Он содержит фазу, код, состояния маршрутов и число восстановлений. В нём нет пароля прокси, телефона, ключа сессии, API hash, содержимого чатов и QR-токена. События `web_route` / `web_*` есть и в журнале приложения.

| Код / фаза | Что делать агенту |
| --- | --- |
| WebPageLoaded / waiting_qr | HTML открылся; ждать готовый QR. Это ещё не вход. |
| WebQrReady / authorizing | QR отрисован; приложение подтверждает его импортированной сессией. Не запускать вторую задачу параллельно. |
| proxy_tunnel / routes.status=failed | Прокси не открыл соединение к указанному серверу Web. Сверить протокол/доступ провайдера к этим именам. Не переимпортировать рабочую сессию и не выключать TLS. |
| WebQrNotReady | После одной очистки дискового кеша QR так и не появился. Смотреть маршруты. Если туннели ready, проверить ошибки веб-клиента / системное время / WebView2; передать отчёт вместо догадок о блокировке аккаунта. |
| WebQrUnreadable | QR отрисован, но не декодирован. «Обновить» начинает новую попытку. При повторе сохранить отчёт и снимок окна без отображения действующего QR третьим лицам. |
| WebSessionApprovalFailed | Читать точный результат в журнале Telegram и отчёт проверки сессии. При отозванной сессии нужен обычный вход/актуальная сессия; FloodWait нужно дождаться. |
| WebTwoFactorRequired / password | Пользователь вводит 2FA на официальной странице; автоматических попыток подбора нет. |
| WebAccountNotOpened | Telegram принял попытку, но главный экран не появился. Не считать вход успешным. «Обновить» сбрасывает состояние и допускает новую попытку. |
| WebSessionConfirmed / ready | Главный экран появился после подтверждения выбранной импортированной сессией. |
| WebIdentityUnconfirmed / ready | Веб-профиль уже был открыт ранее; соответствие выбранному аккаунту отдельно не подтверждено. Проверить имя на странице. |

Автовосстановление ограничено одной перезагрузкой на попытку и официальными адресами того же DC через назначенный прокси. Исходные данные аккаунта и ограничения Telegram не сбрасываются. Если нужен новый запуск, «Обновить» сбрасывает состояние входа; закрытие веб-окна завершает его локальный мост и задачу входа.

## Проверки

CI проверяет обычную диагностику/repair, маршруты, ожидание реального QR вместо пустого контейнера и настоящий WebView2 → локальный HTTP CONNECT → SOCKS5 → TLS → WebSocket в отдельном Web Worker → появление QR → вызов подтверждения → главный экран. Отдельный сценарий проверяет ошибку подтверждения и повтор через «Обновить». Сетевые серверы и аккаунты в тестах синтетические; проверка реального аккаунта на ПК остаётся отдельным шагом приёмки.
