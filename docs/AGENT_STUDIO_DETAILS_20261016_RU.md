# Зависание на «Информация» в YouTube Studio — инструкция агенту

Ветка: `fix/studio-details-chain-20261016`. База: актуальный main `84d8ee599ed44775f5008241a057e13000a6bd95` (включает объединение `bb9e7cb`). Перед обновлением прочитать `docs/AGENT_MAIN_20261016_RU.md`.

## Что известно, а что ещё проверить

Пользователь подтвердил: файл передаётся и заканчивает загрузку, но название не очищается и шаги «Далее» не начинаются. На скриншотах открыт экран «Информация»; на одном виден завершённый copyright-check, на другом — 38% и подтверждение перезагрузки сайта. Журнал с ПК к этому сообщению не приложен. Точную причину конкретной попытки без него подтвердить нельзя.

Подтверждён отдельный дефект main: при `context.setDefaultTimeout(10000)` и посимвольном вводе 959-символьного описания с задержкой 18 мс Playwright обрывал ввод примерно через 10 секунд. Это воспроизведено, но не объясняет отсутствие самого первого ввода заголовка. Прежние тесты использовали короткий текст и задержку 1 мс, поэтому пропускали дефект.

Для остановки перед заголовком проверен дополнительный локальный сценарий: вложенный редактор внутри общего окна загрузки, кнопки/прогресс в общем footer, нередактируемая обёртка `#textbox` вокруг редактируемого поля. Прежний код выбирал внутреннее окно и мог считать обёртку вторым полем. Это регрессионный сценарий, а не снятый DOM пользователя; соответствие конкретной версии Studio на ПК проверить по диагностике.

## Изменения

- Выбирается внешнее активное окно всей загрузки, включая footer; скрытые старые окна не используются. Активность проверяется и по видимым дочерним полям/диалогу: у оболочки с нулевой шириной/высотой и вынесенным позиционированием дочернего диалога собственный прямоугольник может быть нулевым. Такой случай проверен тестом. Несколько отдельных активных окон считаются неоднозначностью.
- Для названия/описания выбираются видимые редактируемые элементы, затем поле явно фокусируется. Ввод остаётся через клавиатуру: выделить, Delete, напечатать, сверить текст. Обёртки и рекомендации хештегов не становятся полем ввода.
- Посимвольный ввод разбит на небольшие блоки с рассчитанным таймаутом каждого действия. Бюджет всей формы учитывает длину текста, а описание сообщает прогресс в символах. Нет единого 10-секундного лимита на всё описание.
- Отдельные события: `file_selected` → `studio_editor` → `metadata_title` → `metadata_description` → `metadata_options` → `metadata_tags` → `metadata_ready` → `upload_transfer` → `studio_steps` → `studio_schedule` → `studio_verify` → `item_confirmed`. В десктопной очереди эти события отображаются как существующие активные состояния.
- Прогресс передачи читается только из видимых индикаторов текущего окна. Отсутствие индикатора больше не даёт 20 минут молчаливого ожидания: через 30 секунд выводится конкретная ошибка. Copyright-check сам по себе не объявляется отказом; обязательные ограничения YouTube не обходятся.
- Диалог `beforeunload` во время работающей Studio-задачи отменяется, чтобы перезагрузка не уничтожала незавершённую форму. Для намеренного выхода сначала остановить задачу. Другие неизвестные подтверждения не принимаются автоматически.
- JSON-диагностика дополнена структурой окон и полей, их редактируемостью, фокусом, длиной текста и количеством кнопок. Содержимое описаний/полей и данные сессий в эту структуру не записываются.

Автопрогрев/просмотры Shorts, настройки профилей, рынки и политика `StudioPending` из main не изменены. Не возвращать блокировку повторной загрузки и не удалять черновики автоматически.

## Обновление на ПК

1. Остановить задачи и закрыть VideoBatch. Сделать резервную копию `%LOCALAPPDATA%\VideoBatchDesktop\` и `D:\VideoBatch\VideoBatch\`. Не закрывать пользовательские профили Dolphin.
2. Проверить `git status` в `D:\VideoBatch\repo`. Не применять `reset --hard`, `git clean` и команды очистки пользовательских данных. При собственных изменениях сохранить их коммитом или использовать отдельный worktree.
3. Подтянуть ветку:

   ```powershell
   git fetch origin
   git switch --track origin/fix/studio-details-chain-20261016
   npm ci --prefix tools/uploader --ignore-scripts
   dotnet build VideoBatch.csproj -c Release
   ```

   Если ветка уже существует: переключиться на неё и выполнить `git pull --ff-only`. В новый каталог установки переносить EXE, DLL, `runtimes` и все актуальные JS/package-файлы `tools/uploader` вместе. Сохранить существующие `node.exe`, прочие runtime-зависимости и пользовательские данные; зависимости uploader установить через `npm ci`. Готовый CI-пакет называется `VideoBatch-Studio-Details-Update`.
4. Записать реальный `git rev-parse HEAD` в `SOURCE_COMMIT.txt`. В первом журнале загрузки должен быть **`Worker 2026-10-16-studio-details-v3`**. Старый marker v2 означает, что запущен старый worker.

Отдельно проверяются 959 символов на настоящей скорости, отмена перезагрузки и игнорирование скрытого старого прогресса.

## Приёмка на пользовательском Dolphin

Сначала один выбранный профиль и одно разрешённое тестовое видео. До запуска сохранить журналы прежней неудачной попытки; не чистить исходники и черновики вслепую.

- Визуально убедиться, что название действительно выделяется, удаляется и печатается заново, даже если оно совпадает с названием файла. Затем должны пройти «Развернуть», сохранённые ответы о рекламе/ИИ и «Далее».
- Ответы о рекламе/ИИ должны соответствовать содержимому; ветка не подменяет эти настройки постоянным «Нет».
- При остановке сразу сохранить строки журнала от worker marker до ошибки из `%LOCALAPPDATA%\VideoBatchDesktop\diagnostics\app-*.jsonl`, а также `youtube-studio-*.json` из каталога диагностик worker. Последний путь выводится событием `diagnosticFile`. Если событие не показано, искать этот файл в каталоге данных приложения, не только в папке EXE.
- Если последний этап `file_select`, но нет `file_selected`, смотреть передачу файла. Если есть `studio_editor`, но нет `metadata_title`, смотреть структуру/редактируемость полей и выбранное окно. Если появился `metadata_title`, смотреть конкретную ошибку фокуса/очистки/ввода. Не заменять это новой попыткой загрузки или изменением случайных пауз.
- После успеха одного ролика проверить выбранную пользователем очередь. Не обещать исправление конкретного ПК только на основании локальных страниц и CI.

Главная цель приёмки: получить либо подтверждённое сохранение ролика с расписанием, либо точную ошибку этапа и диагностику, без бесконечного ожидания и без автоматической повторной передачи файла.
