# Инструкция Cursor: безопасно принять и проверить HTTP/cookies-тест

Эта инструкция специально ограничивает задачу. Не расширяй её и не переписывай рабочий загрузчик.

## Результат, который должен получиться

Отдельная программа `VideoBatch.HttpTest.exe`:

- читает существующие аккаунты из `%LocalAppData%\VideoBatchDesktop\settings.xml`;
- создаёт собственный снимок в `%LocalAppData%\VideoBatchDesktop-HttpTest`;
- не сохраняет ничего в рабочий `settings.xml`;
- запускает ровно один Dolphin Profile ID;
- проверяет, что профиль действительно работает через прокси;
- использует текущую авторизацию/cookies этого Dolphin-профиля только в памяти;
- загружает ровно один файл через HTTP-протокол YouTube из контекста Dolphin;
- ставит одну отложенную публикацию;
- оставляет профиль открытым для ручной проверки результата.

## Жёсткие запреты

1. Не менять и не форматировать:
   - `VideoBatch.csproj`;
   - `src/Uploader.cs`;
   - `src/Core.cs`;
   - `src/UI.cs`;
   - `src/Windows.cs`;
   - `tools/uploader/worker.js`;
   - `tools/uploader/worker-tiktok.js`;
   - рабочий `VideoBatch.exe`.
2. Не переносить код теста в основной EXE до успешного живого теста.
3. Не экспортировать cookies в файл и не выводить cookies/API-токен/пароли прокси в терминал или лог.
4. Не добавлять `youtube-up`, Selenium, Python, mitmproxy или новые npm-пакеты.
5. Не отключать проверки IP и канала ради прохождения теста.
6. После начала передачи файла не делать автоматический повтор: сначала человек проверяет Studio, иначе возможен дубль.
7. Не коммитить `settings.xml`, логи, job JSON, `node.exe` или `node_modules`.

## Шаги в Cursor

Выполняй команды по одной и останавливайся на первой ошибке.

```powershell
git fetch origin
git switch feature/youtube-http-dolphin-test
git pull --ff-only origin feature/youtube-http-dolphin-test
git status --short
```

Ожидается чистая ветка. Затем проверь, что рабочие файлы не отличаются от `main`:

```powershell
git diff --exit-code origin/main -- VideoBatch.csproj src/Uploader.cs src/Core.cs src/UI.cs src/Windows.cs tools/uploader/worker.js tools/uploader/worker-tiktok.js
```

Команда обязана завершиться без diff. Если есть изменения — ничего не исправляй автоматически, покажи diff владельцу.

Проверь наличие локального комплекта, который уже использует VideoBatch:

```powershell
Test-Path .\tools\uploader\node.exe
Test-Path .\tools\uploader\node_modules\playwright-core
```

Обе команды должны вернуть `True`. Затем:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Build-HttpTest.ps1
```

Скрипт сам запускает Node-регрессии, собирает отдельный проект и создаёт независимую папку `artifacts\http-test`. Нельзя копировать результат поверх рабочего `VideoBatch.exe`.

## Первый живой тест — только один аккаунт

1. Сделай резервную копию `%LocalAppData%\VideoBatchDesktop\settings.xml` обычным копированием.
2. Запусти Dolphin Anty и оставь его открытым.
3. В обычном VideoBatch у выбранного аккаунта один раз выполни `Проверить профили`, чтобы сохранился актуальный `ExpectedIp`.
4. Закрой в Dolphin только выбранный профиль, если он уже открыт. Сам Dolphin не закрывай.
5. Возьми короткий тестовый ролик, повторная публикация которого не нанесёт ущерба.
6. Запусти `artifacts\http-test\VideoBatch.HttpTest.exe`.
7. Убедись, что в списке уже видны существующие аккаунты. Ничего заново не подключай.
8. Выбери один аккаунт и один файл. Проверь автоматически очищенный заголовок; программа не должна молча обрезать его.
9. Поставь публикацию минимум на 30 минут вперёд.
10. Нажми `Загрузить 1 тестовое видео` и ещё раз проверь аккаунт, Profile ID, IP и время в окне подтверждения.
11. Дождись строки `done` со ссылкой. Профиль останется открытым.
12. В YouTube Studio вручную проверь одновременно четыре факта:
    - появился ровно один ролик;
    - заголовок совпадает полностью;
    - статус — запланировано;
    - дата и время совпадают.
13. Проверь, что резервная и текущая рабочая конфигурация не отличаются:

```powershell
Get-FileHash "$env:LOCALAPPDATA\VideoBatchDesktop\settings.xml"
```

Тестовая программа также сама сверяет SHA-256 рабочего файла до и после запуска.

## Если тест остановился

- До стадии `upload`: файл на YouTube не передавался; исправь указанную причину и можно повторить.
- На стадии `upload` или позже: не повторяй автоматически. Сначала открой оставленный Dolphin-профиль и проверь `Контент`/`Черновики` в Studio.
- `Прокси не используется`: не отключай проверку; исправь прокси профиля.
- `Открыт другой YouTube-канал`: исправь привязку Profile ID/Channel URL.
- `sessionToken`/`SAPISID`: войди в YouTube Studio вручную в этом Dolphin-профиле и повтори один раз.
- Ошибка после получения `videoId`: ролик уже может существовать; проверка Studio обязательна.

Лог теста: `%LocalAppData%\VideoBatchDesktop-HttpTest\http-test.log`.

## Отчёт, который Cursor должен вернуть владельцу

Не пиши «всё работает», если живой тест не выполнен. Верни строго:

```text
Ветка: feature/youtube-http-dolphin-test
Коммит: <sha>
Рабочие файлы main не изменены: ДА/НЕТ
Node-регрессии: PASS/FAIL
Сборка VideoBatch.HttpTest.exe: PASS/FAIL
Аккаунты из settings.xml появились: ДА/НЕТ
Прокси IP подтверждён: ДА/НЕТ
Получен videoId и URL: ДА/НЕТ
В Studio ровно один ролик: ДА/НЕТ
Заголовок совпадает: ДА/НЕТ
Отложенное время совпадает: ДА/НЕТ
Рабочий settings.xml не изменён: ДА/НЕТ
Лог при ошибке: <только текст ошибки, без секретов>
```

Только если все строки после сборки имеют `PASS/ДА`, можно отдельно планировать добавление второй кнопки в основной интерфейс. До этого основной путь считается единственным рабочим и остаётся нетронутым.
