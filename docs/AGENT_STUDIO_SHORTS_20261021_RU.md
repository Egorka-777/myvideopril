# Studio: Shorts и завершение очереди — v19

Ветка `fix/studio-shorts-queue-20261021` от main `4a1a2299b15dbc210ef060e6ff229b9cb6bc169f`. Сохранены последние правки прогревочных роликов, интерфейса и банков описаний из main. Приложение не переустанавливать с удалением данных, аккаунты и прокси не переимпортировать.

## Что обнаружено

На скриншотах — ошибки проверки описания, неоднозначный поиск двух кнопок «Копировать ссылку» и недоступная «Создать». Полных JSON-журналов с ПК в этом задании нет; точную структуру его живой страницы не подтверждали. При этом в исходниках main найдены воспроизводимые ошибки:

- `fieldSame()` принимал даже пустой/неполный префикс за полный текст. Затем код заменял ожидаемый префикс содержимым DOM и продолжал с очередного смещения исходной строки — потерянный текст мог пропускаться. Новый тест запускает код main на поле с ограничением длины: старый код принимает 4 символа вместо 9, новый отклоняет результат.
- Любые кнопки шаринга/продвижения, а также неактивная «Опубликовать» могли считаться успешной публикацией. Таймаут сохранения перехватывался, после него запускались закрытие и повторные dismiss, включая Escape. Shorts не проверялись по сохранённому ID.
- Проверка длинного видео опять сравнивала показанные дату/часы/пояс буквально. Studio может показать тот же сохранённый момент в часовом поясе браузера. Восстановлено сравнение UTC-момента; перед самой отправкой по-прежнему строго проверяются поля приложения.

## Новая цепочка

Файл → точный ввод названия/описания → подтверждённое завершение передачи → ID → настройки → одно нажатие публикации/планирования → экран завершения либо закрытый мастер → чтение сохранённых метаданных и доступа по ID → сохранение результата в приложении → ожидание доступной «Закрыть» → одно нажатие и подтверждение исчезновения окна → доступная «Создать» для следующего файла.

Shorts: **без загрузки и проверки изображений превью**, сразу публично, без планирования. Длинные видео: превью и расписание сохранены. Две кнопки «Копировать ссылку» допустимы: они вообще не используются как уникальная кнопка завершения.

Для описания — ввод клавишами, перенос строки Shift+Enter, точная сверка частей и итогового текста. Исходный текст не подменяется содержимым DOM. При замене редактора допускается один повтор только этого поля. Нет force-кликов сквозь неизвестный DIV, нет удаления затемнений из DOM и серии Escape.

Кнопка «Закрыть» может быть временно неактивна: ожидается до 90 секунд с сообщениями журнала. Она нажимается один раз. Неактивная «Опубликовать», исчезновение индикатора загрузки или наличие шаринга сами по себе успехом не считаются. Таймаут подтверждения не запускает повторную публикацию: сначала проверяется уже созданный ID. При временно старых данных допускается один повтор чтения того же ID в проверочной вкладке; мастер загрузки не перезагружается. Если сохранение не подтверждено, незавершённый мастер сохраняется и следующий файл не передаётся.

Результат проверенного видео записывается **до** закрытия окна. Если закрытие сломалось, уже опубликованный ролик не забывается. Для незавершённой записи сохраняется `studioVideoId`: при новом запуске известный ID можно проверить без повторной отправки; неизвестный ID требует проверки черновика. Старый `StudioPending` больше не стирается без проверки при запуске Studio.

Пользователь намеренно повторяет один тестовый файл. **Запрета по хешу или имени файла нет.** Повторный выбор файла как новой задачи допустим; нельзя только молча считать незавершённую старую отправку новой. Не удалять существующие видео на YouTube автоматически ради теста.

## Установка

1. Дождаться остановки задач, закрыть VideoBatch. Сделать резервную копию EXE/DLL/runtimes, `tools/uploader` и пользовательских данных.
2. Скачать **VideoBatch-Studio-Shorts-Update** из успешного Actions **YouTube Studio RU EN upload** этой ветки. Сверить `SOURCE_COMMIT.txt` с HEAD проверяемой ветки.
3. Заменить **EXE + DLL/runtimes + все JS и package-файлы `tools/uploader`**. Одних JS недостаточно: обновлён C#-контракт сохранённого ID. Сохранить node.exe и установленные сторонние инструменты. Выполнить `npm ci --prefix tools/uploader --ignore-scripts` в папке приложения, где существует этот путь.
4. Из исходников: сохранить местные изменения, `git fetch origin`, `git switch fix/studio-shorts-queue-20261021`, `git pull --ff-only`, `dotnet build VideoBatch.csproj -c Release -p:ApplicationIcon=`. Не применять reset/clean к пользовательской рабочей копии.
5. Новый запуск должен показывать **`2026-10-21-studio-shorts-queue-v19`**. Если виден v18/v13/v11, искать старую копию EXE/worker и фактический путь запуска. Банки описаний и аккаунты сохраняются.

## Контроль на ПК и разбор сбоя

Сначала один Shorts; после успешного завершения — два подряд. Можно использовать тестовый исходник повторно через новый выбор файла. Проверить в Studio созданные ID. Ожидаемые этапы: `metadata_description` → `upload_transfer` → `studio_publish` → `studio_verify` → `item_confirmed` → `studio_close` → `studio_ready` → следующий `file_select`.

Если опубликовано, а Close долго недоступна, не добавлять Escape/force и не нажимать «Опубликовать» второй раз. Дождаться сообщения, сохранить диагностику. Подтверждённый ID уже сохранён; повтор этого задания не должен создавать его заново. Если раньше агент стёр pending или использовал старый EXE, сначала сверить реальные видео в Studio с записями приложения.

При ошибке сохранить полный `diagnostics/youtube-studio-*.json`, журнал с маркером и `SOURCE_COMMIT.txt`. Не ограничиваться скриншотом сообщения. Из диагностики важны последний этап, состояние окна завершения, ID, доступность кнопок и фокус/длины полей; текст описания и секреты в диагностический файл не добавляются.

Не заменять причины увеличением всех таймаутов и не объявлять прогон на аккаунте успешным по тестовым страницам. Контроль на ПК необходим: среда разработки не подключалась к его Dolphin и не публиковала в его аккаунты.
