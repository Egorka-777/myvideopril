# YouTube Studio: превью и планирование — 19.10.2026

Ветка `fix/studio-state-flow-20261019`, база main `a7148b7c18b17d65087e79445c8789fef7ba50fb`.
Маркер worker: `2026-10-19-studio-state-v4`.

## Что исправлено и что подтверждено

- На воспроизводимом примере старый код main ожидает Next, когда уже открыт экран Visibility без старого компонента `ytcp-visibility-scheduler`. Теперь опрашиваются текущий шаг и конечный экран вместе.
- Один клик Next должен сопровождаться изменением текущего шага/его элементов. Если переход не подтверждён, повторные клики прекращаются с ошибкой.
- Обёртка `ytcp-button` и её вложенная нативная кнопка считаются одним действием. Карточка Schedule и финальная кнопка Schedule выбираются отдельно. Финальная кнопка для расписания должна явно предлагать планирование; Publish вместо неё не нажимается.
- После выбора карточки ждём появления полей. Дата, время и пояс проверяются до сохранения и в отдельной вкладке редактора после него.
- Проверка превью больше не прокручивает страницу к каждой картинке. Один раз показывается область превью, затем сравнивается видимое изображение; повторные сравнения одного источника ограничены. Проверка в окне загрузки не вызывает reload. Перезагрузка остаётся только в отдельно вызываемом режиме save/verifyReload редактора уже существующего видео.
- ID созданного ролика сообщается приложению до проверки превью, чтобы ошибка картинки не теряла связь с существующим черновиком.
- JSON диагностики содержит build, последний этап, фактические переходы главной страницы, сетевые ошибки без URL query/заголовков/тела запросов и распознанные элементы текущего шага. Изображения аккаунта и переписка в репозиторий не добавлялись.

Не подтверждена причина именно пользовательского мерцания: без лога нельзя утверждать, что это были настоящие reload. Исправлен подтверждённый механизм нежелательной прокрутки; новая диагностика позволяет отличить её от навигации и сетевого сбоя.

Поведение актуального main для Shorts сохранено: сразу Public, без превью/расписания. Для Long — расписание и выбранное превью. Глобальную настройку записи тегов не меняли: worker использует настройки/значения Studio; браузерные тесты записи тегов явно включают `writeTags:true`.

## Обновление на ПК

1. Найти фактическую папку запуска и проверить SOURCE_COMMIT.txt. Ранее использовались `D:\VideoBatch\repo` и `D:\VideoBatch\VideoBatch`; не считать их актуальными без проверки.
2. Закрыть VideoBatch и его конкретный worker. Сохранить копию папки приложения и `%LOCALAPPDATA%\VideoBatchDesktop`. Данные, профили, прокси и настройки не удалять. Не завершать все процессы node и профили Dolphin подряд.
3. Получить именно эту ветку, сохранив локальные изменения. Не выполнять reset --hard/clean. Можно создать отдельный checkout:

```powershell
git fetch origin fix/studio-state-flow-20261019
git worktree add ..\repo-studio-state origin/fix/studio-state-flow-20261019
```

4. Вариант А: скачать `VideoBatch-Studio-State-Update` из успешного workflow `YouTube Studio RU EN upload` этой ветки. Обновить EXE, DLL, runtimes и tools/uploader вместе. Проверить SOURCE_COMMIT.txt артефакта.
5. Вариант Б: в новом checkout выполнить:

```powershell
npm ci --prefix tools/uploader --ignore-scripts
dotnet build VideoBatch.csproj -c Release -p:ApplicationIcon=
```

Скопировать EXE/DLL/runtimes из `bin\Release\net48` и весь `tools\uploader` с установленным node_modules в рабочую папку, сохранив остальные модули. Записать текущий SHA в SOURCE_COMMIT.txt. Если использовался готовый артефакт, выполнить npm ci из установленной папки приложения. Не заменять только worker.js или только EXE.

## Приёмка в живом Studio

Егор уже поручил проверить публикацию своих выбранных видео; использовать только предоставленный аккаунт и тестовый ролик, не запускать массовую очередь при диагностике.

1. В логе должен появиться `Worker 2026-10-19-studio-state-v4`. Иначе проверить запущенную копию EXE и tools/uploader.
2. Long: один ролик с превью, дата/время в будущем. Проверить новое название и описание, затем подтверждённую картинку. На экране «Доступ» Next больше не нужен: карточка «Запланировать публикацию / Schedule», дата/время/пояс, «Запланировать / Schedule».
3. Успех — не только исчезновение окна загрузки: редактор существующего ID должен подтвердить расписание и превью после сохранения. Только затем очередь переходит к следующему видео. Проверить RU и EN, когда соответствующие аккаунты доступны.
4. При ошибке остановить очередь. Не запускать тот же исходник повторно наугад: в текущем main пользователь ранее разрешил повторную загрузку, строгой глобальной блокировки StudioPending там нет. Сначала найти уже созданный черновик по StudioVideoId/ссылке и состоянию очереди.
5. Отчёт находится в `diagnostics` рядом с каталогом заданий worker: `youtube-studio-<time>-<pid>.json`; точный путь worker сообщает событием `diagnostic`. Сопоставить `flow.lastStage`, `flow.navigations`, `flow.networkErrors`, `wizard`, `controls`. Не заменять кнопку очередным переводом без просмотра этих полей. Не публиковать логи с токенами, данными сессий или аккаунтов.
