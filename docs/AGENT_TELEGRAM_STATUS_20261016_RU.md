## Что было неверно в индикации

На скриншоте владельца был результат «Нет связи», но рядом время в колонке «Проверен» и внизу «Задача завершена». Это не подтверждало успешный вход. Причину реального сбоя нельзя определить по этому скриншоту: нужны этап/код и проверка маршрута с ПК.

Теперь последняя попытка, последняя успешная проверка, ошибка аккаунта и результат прокси хранятся отдельно. Зелёный аккаунт появляется только после авторизованного `get_me`, с проверкой ожидаемого user_id. Завершение процесса не подменяет итог проверки; при ошибках итог задачи помечается ошибкой. После 15 минут успешная проверка аккаунта становится устаревшей и просит перепроверку. Это снимки результатов, а не постоянный онлайн-мониторинг.

Прокси проверяется настоящим туннелем с авторизацией до production DC Telegram: открытый порт сам по себе не считается успехом. Отдельная проверка прокси использует DC2; проверка аккаунта — DC из его сессии. Успешный TCP-туннель ещё не доказывает успешный MTProto-вход, поэтому два состояния разделены. Неработающий прокси не приводит к скрытому прямому подключению и не означает бан аккаунта.

Число блокировок в прокси — количество **сохранённых аккаунтов с текущим результатом blocked** на этом адресе. Это не полная история блокировок за всё время и не доказательство того, что прокси вызвал блокировку. Удалённые/деактивированные аккаунты отделены от явного сообщения Telegram о бане. Старые результаты требуют повторной проверки.

## Установить обновление полностью

1. Закрыть приложение. Сохранить резерв папки установки и `%LOCALAPPDATA%\VideoBatchDesktop`. Сохранить все аккаунты, настройки, шаблоны, историю, локальные компоненты Node/FFmpeg/Нарезчика и существующее хранилище Telegram.
2. В отдельной рабочей папке:

```powershell
git clone --branch feat/telegram-status-invites-20261016 --single-branch https://github.com/Egorka-777/myvideopril.git myvideopril-telegram-status
cd myvideopril-telegram-status
dotnet build VideoBatch.csproj -c Release -p:ApplicationIcon=
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\telegram\setup.ps1
```

3. Переносить **EXE/config, DLL из `bin/Release/net48`, папку `runtimes`, полную `tools/telegram` из ветки**. Для WebView2 нужны `Microsoft.Web.WebView2.Core.dll`, `Microsoft.Web.WebView2.WinForms.dll`, соответствующий процессу `WebView2Loader.dll` из `runtimes`, а для чтения QR — `zxing.dll`. Не обновлять один EXE. Сохранить остальные компоненты установки. JS/package-файлы `tools/uploader` должны соответствовать ветке, при изменении lock выполнить `npm ci --prefix tools/uploader`.
4. На ПК нужны Python 3.11 x64 с Launcher и **Microsoft Edge WebView2 Evergreen Runtime**. Это runtime, а не только установленный браузер Edge. Проверить наличие; если отсутствует — поставить официальный Evergreen Runtime: https://developer.microsoft.com/microsoft-edge/webview2/#download-section . Платный сервис не нужен.
5. Версия worker в журнале: **`2026-10-16-telegram-status-v3`**. Проверить, что рядом присутствует новый **`tools/telegram/web_proxy.py`**. Зависимость `python-socks` обязательна.

## Проверка одного аккаунта и прокси

1. Telegram → Прокси → выбрать назначенный адрес → **Проверить**. Увидеть доступность туннеля или причину ошибки. При ошибке проверить протокол/host/port/логин/пароль и возможность доступа к Telegram через этот прокси именно с ПК. Не заменять авторизацию прокси одним IP.
2. Telegram → Аккаунты → выбрать аккаунт → **Проверить**. Видны этапы: прокси, затем аккаунт. «Попытка» обновится даже при ошибке; «Работает» требует подтверждения Telegram. Причина и код доступны в строке/подсказке/карточке/журнале.
3. Повторить после перезапуска: назначение, результат, успешная дата и ошибки сохраняются. Реальные пароли/ключи/содержимое JSON/TData в чат/GitHub/отчёт не копировать.
4. Красный Dolphin в глобальной шапке скрыт именно в Telegram: локальный браузер Dolphin для этих операций не требуется. Получение настроек прокси из облака Dolphin по сохранённому токену остаётся отдельной функцией.

## Telegram Web внутри приложения

Аккаунт → **Открыть Telegram**. Открывается отдельное окно приложения с официальным `https://web.telegram.org/a/`, собственным браузерным профилем для этого аккаунта и тем же назначенным прокси. HTTP/SOCKS4/SOCKS5 с авторизацией идут через временный локальный CONNECT-мост; bridge без авторизации и запросы к посторонним доменам отвергает. При настроенном неработающем прокси прямой маршрут не включается. В явном режиме «Без прокси» системный прокси браузера тоже отключён.

При первом входе дождаться штатного QR на экране и нажать **«Войти этим аккаунтом»**. Приложение считывает только QR из контейнера экрана входа официального Web A, подтверждает новую веб-сессию стандартным `auth.acceptLoginToken` от импортированной сессии. Ключ сессии в JavaScript/localStorage вручную не внедряется; QR из сообщений/чатов не принимается. При 2FA пароль вводится вручную в официальной веб-странице; другие сессии не завершаются. Если QR истёк — обновить и повторить, без автоматических бесконечных попыток.

Веб-профиль хранится отдельно в `%LOCALAPPDATA%\VideoBatchDesktop\telegram\web\<id>`, под ACL текущего пользователя Windows. Это браузерное хранилище, а не часть DPAPI-файла `telegram.vault`. Не включать его в логи или репозиторий. Веб-окно не выдаёт факт открытия страницы за успешную проверку аккаунта; визуально сверить профиль. При закрытии окон bridge останавливается.

Если Telegram поменяет селектор своего экрана QR, приложение откажется подтверждать вход, а не будет сканировать произвольные QR на странице. Актуальная проверенная структура upstream: `#auth-qr-form .qr-container` в `Ajaxy/telegram-tt/src/components/auth/AuthQrCode.tsx`. Полный живой вход владельца, истечение QR и 2FA нужно проверить на ПК; офлайн-тесты их не заменяют.

## Первый тест приглашений

1. Создать свою тестовую группу или использовать свой канал. Выдать выбранному **аккаунту-отправителю** права администратора с добавлением участников. В этой версии проверка намеренно требует эти права, даже если настройки конкретной группы позволяют приглашать обычным участникам. Приложение не создаёт группу автоматически, не вступает скрытно по ссылке и не меняет админ-права приглашаемых.
2. Вкладка **Приглашения** → выбрать отправителя → вставить ссылку `t.me/…`, `@username`, известный ID или приватную ссылку сообщества, где отправитель уже состоит → **Проверить права**. Это чтение, приглашения пока не отправляются.
3. Ввести @username одного своего тестового пользователя, который ожидает приглашение. Или **Список из файла**: TXT, CSV, JSON. Это список **приглашаемых пользователей**, а не файлы авторизации аккаунтов-отправителей.
4. Оставить **«Обработать не более: 1»**, паузу 60 сек → **Запустить**. Права проверяются повторно при реальном старте. Лимит — максимум строк пользователей на этот запуск, а не обещание безопасной суточной квоты Telegram.
5. Проверить результат в журнале и в самой группе. Ответ RPC без фактического членства не считается приглашением. Приватность/неизвестный пользователь показываются отдельно. FloodWait/PeerFlood, отсутствие прав и сетевой сбой останавливают задачу; автоматической смены аккаунта, обхода ограничений и повторной отправки неопределённого запроса нет. История сохраняется до отправки и защищает от повторов после перезапуска.

### Файлы пользователей

TXT: `@username`, `https://t.me/username` или положительный user_id; один на строке (пробелы/запятые также допустимы). Дубли удаляются без учёта регистра.

CSV: столбец `username` или `user_id`/`telegram_id`/`id`; если есть username и ID, предпочтение username. Поддерживаются запятые/точки с запятой и quoted-поля. Одноколоночный CSV может быть без заголовка. UTF-8/BOM/UTF-16 BOM, при невалидном UTF-8 — Windows-1251. Предел 4 МБ/10 000 строк.

JSON: массив строк/чисел/объектов либо `{ "users": [...] }`. У объектов поля username/user_id/id. Неизвестные и некорректные строки отмечаются при загрузке; нормализованный принятый список виден до запуска.

Числовой ID не заменяет account-specific access_hash. Для ID используются доступные выбранному аккаунту собственные диалоги (до 100) и контакты; неизвестные пользователи не «додумываются», в журнале будет «Не найден». Для первого теста использовать @username. Access_hash от другого аккаунта не переиспользуется.

## Что проверено автоматически / что обязательно проверить на ПК

Автотесты используют синтетические сессии и локальные сокеты: импорт JSON/TData, дедуп, сохранность исходников, DPAPI; статусы попытка/успех/ошибка/устаревание и FloodWait; отдельная реальная SOCKS5-авторизация/туннель; отсутствие прямого обхода; лимит строк и неизвестный ID; чтение прав без приглашений; приватная ссылка без автоматического вступления; QR-декодирование и проверка user_id перед acceptLoginToken; локальный WebView2 Basic proxy auth и реальный native-render; CONNECT bridge с авторизацией, двунаправленной передачей и блокировкой чужих адресов; существующие Studio/Telegram/JS проверки.

Живые учётные данные владельца, реальный прокси/токен Dolphin и приглашение реального пользователя на стороне автора кода не использовались. Агент должен проверить полный путь **одного** разрешённого владельцем аккаунта, включая визуальный вход в Web и одно ожидаемое приглашение. Если ошибка — сохранить безопасный этап/код и точную версию компонентов; не подменять её зелёной индикацией и не расширять тест на все аккаунты.
