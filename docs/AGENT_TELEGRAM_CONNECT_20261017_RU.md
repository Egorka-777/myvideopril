## Задача агенту на ПК

Установить обновление целиком и проверить ОДИН аккаунт пользователя по цепочке ниже.
Не объявлять задачу завершённой по одному успешному импорту или открытому окну QR.
Не удалять настройки, vault, исходные TData/.session, браузерные профили и другие сессии Telegram.
Не загружать файлы авторизации, пароли, API hash, QR-токены и строки прокси с паролем в GitHub/отчёт.

### Установка

1. Закрыть приложение. Сохранить резервную копию установленной папки и каталога данных Telegram.
   Обычно данные — `%LOCALAPPDATA%\VideoBatchDesktop\telegram`, но при переносном режиме проверить фактический путь в существующей установке. Сохранить `telegram.vault` и `web`.
2. В репозитории выполнить `git status --short`; локальные изменения сохранить отдельно. Затем:
   ```powershell
   git fetch origin
   git switch --track origin/fix/telegram-connect-flow-20261017
   ```
   Если локальная ветка существует: `git switch fix/telegram-connect-flow-20261017`, `git pull --ff-only`.
   Не выполнять `reset --hard`, `clean` и не переключать main принудительно.
3. В GitHub Actions → **Telegram workspace** выбрать успешный запуск именно этой ветки и скачать **Telegram-Connect-Update**.
   Распаковать целиком: EXE, DLL, `runtimes/win-x86/native`, `runtimes/win-x64/native`, `tools/telegram`, `tools/uploader`.
   Сверить `SOURCE_COMMIT.txt` с коммитом запуска. Одного EXE недостаточно.
   Существующие Node/node_modules, FFmpeg, пользовательские файлы и настройки оставить.
   При сборке вручную: `dotnet build VideoBatch.csproj -c Release -p:ApplicationIcon=`; устанавливать весь выходной каталог с DLL и workers.
4. Проверить Microsoft Edge WebView2 Runtime. Для новой среды нужен **Python 3.11 x64** с python.org.
   Telegram → Настройки → **Подготовить Telegram**. При импорте/проверке подготовка также запускается автоматически, если среда ещё не проверена.
   Проверяется весь закреплённый набор зависимостей, чтение TData, криптография и создание обоих типов прокси-коннектора.
   Наличие одного `venv/Scripts/python.exe` больше не считается готовностью.
   Успешная подготовка создаёт `runtime.ready` с версией `2026-10-17-telegram-connect-v2`.
5. Если старое окружение создано неподходящим Python и подготовка падает на tgcrypto/PyQt5:
   закрыть приложение, переименовать ТОЛЬКО подкаталог `telegram/venv` в резервный `venv-backup-...`, затем повторить подготовку под Python 3.11 x64.
   `telegram.vault`, `web` и исходники не трогать. Не создавать `runtime.ready` вручную.
   В Linux при самостоятельной проверке нужен доступный C-компилятор для tgcrypto; это не требование ставить компилятор пользователю Windows.

### Файлы аккаунта

На предоставленном пользователем скриншоте магазина есть разные варианты выгрузки: TData, Telethon .session, Pyrogram .session, JSON.
Они представляют разные форматы. JSON с описанием аккаунта сам по себе не авторизует Telegram.

Рекомендуемый первый тест:

1. Скачать **Telethon .session** и соответствующий **JSON** одного аккаунта. Положить рядом с одинаковым базовым именем, например `account.session` и `account.json`.
2. Telegram → **Добавить аккаунты** → выбрать эту папку или парный JSON. Выбрать прокси и оставить «Проверить после добавления».
3. Альтернатива — папка TData или ZIP с ней. При локальном коде-пароле TData ввести его в «Дополнительно». Это локальный код шифрования TData, не облачный пароль 2FA.
4. Pyrogram SQLite тоже распознаётся по таблицам; для неё нужен JSON с API ID/hash именно этой сессии. Несоответствие API или user_id не замалчивается. Не переименовывать Pyrogram в Telethon и не подставлять случайный API hash.
5. Парный JSON имеет приоритет для метаданных. Если рядом есть и `.session`, и `_tdata`, выбор JSON сначала берёт точную `.session`-пару. Импорт всей папки дополнительно найдёт TData; одинаковые ключи авторизации не создают дубликаты.
6. Повторный явный импорт того же ключа обновляет API/метаданные и формат в существующей записи. Название пользователя, заметка, прокси и ограничения Telegram сохраняются. Другой ключ — отдельная сессия. Противоречащий user_id отклоняется.

Исходные файлы читаются без изменения. SQLite не открывается на запись; временная распаковка ZIP удаляется. В Windows сессия сохраняется в DPAPI-vault текущего пользователя.

### Прокси → проверка аккаунта → открытие Web

1. **Прокси → Ещё → Из Dolphin** получает сохранённые настройки прокси, без запуска профиля Dolphin.
   Также доступны прокси из общего списка аккаунтов приложения и ручная строка SOCKS5/SOCKS4/HTTP.
   При необходимости выбрать аккаунт → **Назначить прокси**. Протокол должен совпадать с выданным провайдером; строка `host:port:user:password` без схемы трактуется как SOCKS5.
2. Проверка прокси открывает авторизованный туннель к `web.telegram.org:443`. Это ещё не проверка аккаунта.
   На одну попытку туннеля установлен общий предел 7 секунд, включая DNS/handshake.
3. **Проверить выбранные** проверяет маршрут именно до DC импортированной сессии, затем подключает сессию и получает пользователя Telegram (`get_me`).
   Если DC недоступен, дополнительно проверяется Web: при успехе выводится **«Только Web» / `mtproto_unreachable`**.
   Такой прокси не объявляется подходящим для подключения сессии: нужен доступ к MTProto. Прямого обхода назначенного прокси нет.
   Предел подключения и получения пользователя — 22 секунды после проверки маршрута. При недоступном прокси две диагностические попытки могут суммарно занять до 14 секунд.
4. Состояние **«Работает»** появляется только после ответа Telegram с пользователем. Проверка не доказывает отсутствие всех ограничений аккаунта; права на группу проверяются отдельно.
5. **Открыть Telegram** или двойной щелчок по строке: сначала проверяется подключение. При ошибке остаётся понятная причина в строке и журнале; пустое окно входа не открывается.
6. При успешной проверке запускается официальный **Telegram Web A** во встроенном WebView2 с отдельным профилем аккаунта.
   Авторизованная импортированная сессия подтверждает QR через официальный `auth.acceptLoginToken`.
   Порядок: подключить сессию и подтвердить user_id → прочитать свежий QR из официального окна → принять QR → дождаться главного экрана Web.
   QR не читается до долгой сетевой проверки. При явно истёкшем токене допускается до трёх свежих попыток в рамках того же подключения; потерянный ответ не вызывает повторную авторизацию.
7. При запросе **2FA** пользователь вводит пароль непосредственно на странице Telegram. Не подставлять пароль локального шифрования TData и не сбрасывать другие сессии.
   Если сессия отозвана/не авторизована, из JSON её восстановить нельзя — нужна действующая выгрузка или обычный вход владельца в официальном клиенте.
8. Успех QR-RPC и загрузка аккаунта — разные этапы. Надпись **«Telegram открыт»** и запись журнала `web_ready` появляются после обнаружения главного экрана Web.
   Закрыть/повторно открыть окно: сохранённый вход должен остаться. Нажатие «Стоп» и закрытие окна должны прекратить ожидание QR.

### Приглашения

В интерфейсе — минимальная схема для собственной группы: выбрать аккаунт администратора → вставить группу/канал → проверить права → **Создать ссылку** → копировать.
Ссылка создаёт запрос на вступление: человек открывает её сам, администратор подтверждает в Telegram.
Сообщения, массовые добавления чужих пользователей, рекламные комментарии, обход лимитов и смена аккаунтов для обхода ограничений не добавлены.
Повторное создание ссылки — отдельная операция, старые ссылки можно отозвать в самом Telegram.

## Что проверено автоматически и что проверить на ПК

Автотесты используют синтетические ключи и локальные серверы. Они проверяют форматы, отсутствие изменения исходников, неверную идентичность/API, реальные SOCKS/HTTP-handshake, отказ пароля, отсутствие прямого обхода, границы ожидания, свежий QR и отмену.
Windows workflow дополнительно собирает приложение, проверяет DPAPI, протокол EXE/Python, native WebView2 с авторизацией прокси и чтением реально отрисованного QR, обе архитектуры загрузчика в комплекте и создаёт снимки интерфейса.

Ни действующего аккаунта пользователя, ни его прокси/2FA в среде разработки нет. Внешний вход на этих данных **не подтверждён**.
Агент на ПК должен записать результат каждого этапа: установленный SHA; подготовка; формат импорта; проверка прокси; `get_me`; открытие правильного аккаунта; повторное открытие; остановка; ссылка собственной группы.
Если ошибка остаётся — вернуть безопасные код/этап/время из журнала, без секретов. Например `configuration`, `handshake`, `timeout`, `mtproto_unreachable`, `AuthKeyUnregisteredError`, `AuthTokenExpiredError`.
