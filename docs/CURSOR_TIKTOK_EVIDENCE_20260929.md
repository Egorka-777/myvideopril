# TikTok: безопасное применение изменений на ПК

База анализа: `4fcffa1`, ветка `fix/tiktok-http-and-studio-modal-20260923`.
Изменения: `fix/tiktok-evidence-20260929`, worker `2026-09-29-tiktok-http-v5.4-evidence`.

## Что доказано кодом

UI → TikTok.cs → HttpTikTokUploadRunner → worker-tiktok-http.js →
token/apply → create project → upload/commit → post → сообщение worker → settings.xml.

1. Worker считал существование проекта, созданного ДО post, доказательством публикации.
2. Слова review/private в ошибке превращали отказ в успех.
3. C# помечал всю пачку Published даже без индивидуальных подтверждений.
4. Ошибка browser fetch могла повторить тот же POST другим транспортом.
5. Browser IP и request IP измерялись под перепутанными названиями; browser-проба могла незаметно замениться request-пробой.

Это объясняет ложный отчёт приложения. Это НЕ доказывает конкретную причину отказа TikTok на ПК.

## Что изменено и чего не обещаем

- Ошибка HTTP или вложенного элемента не считается успехом. Project list и текст ошибки не подтверждают post.
- Успешный ответ post означает только принятие запроса. `HttpSubmitted` хранится отдельно от `Published`.
- HTTP-результаты связаны с устойчивым LocalJobId; итог проверяется по каждому элементу.
- Состояние неизвестной попытки сохраняется в settings.xml и блокирует повтор; отмена/перезапуск не разрешают автоматически отправить тот же ролик заново.
- Есть кнопка «Сверить HTTP»: пользователь может подтвердить найденный в Studio ролик. Неизвестные попытки остаются заблокированы. Для подтверждённо отсутствующего ролика повторное добавление — только осознанное действие после сверки.
- HTTP POST не повторяется другим транспортом после браузерной ошибки.
- До загрузки проверяются независимые IP браузера и request-клиента; несовпадение/невозможность проверки останавливает загрузку. Это защита от непроверенного маршрута, НЕ реализация поддержки прокси для request-клиента. При вращающемся прокси проверка может блокировать корректный маршрут. Равенство IP не доказывает маршрут каждого CDN-запроса.
- Интервалы TikTok: 600–1800 секунд. Расписание новой пачки не переиспользуется лишь по одинаковому количеству файлов. Первый слот по текущему правилу приложения: не раньше 15 минут. Это правило кода, не подтверждённое актуальное ограничение TikTok.
- Успех post НЕ подтверждает появление в Studio, окончательную видимость или соблюдение schedule_time сервером.
- Старые ошибочные Published автоматически не сбрасываются: это могло бы создать дубли.
- YouTube и автоматическая сетка просмотров/лайков не менялись.

## Применить без потери локальных правок

1. Определить фактический путь запущенного EXE и каталог данных. Не считать D:\VideoBatch\repo автоматически рабочей версией. Зафиксировать версию worker рядом с EXE.
2. Завершить текущие задачи. Скопировать приложение, settings.xml, очередь, диагностику и staging в отдельный каталог резервной копии. Не коммитить настройки с секретами.
3. В локальном репозитории выполнить `git status --short`, `git branch --show-current`, `git log -5 --oneline`. Сохранить локальные изменения исходников отдельным локальным коммитом; бинарники/секреты оставить в резервной копии. Не выполнять reset --hard, clean -fd и принудительную замену main.
4. `git fetch origin`. Создать integration-ветку от текущего локального коммита с пользовательскими изменениями. В отдельном worktree этой integration-ветки выполнить `git merge --no-ff origin/fix/tiktok-evidence-20260929`.
5. Конфликты разбирать по смыслу. Сохранить местные изменения интерфейса и настройки, одновременно перенести контроль каждого HTTP-элемента, отсутствие слепого replay и новые поля модели. Не выбирать целиком ours/theirs без просмотра.
6. `npm ci --prefix tools/uploader --ignore-scripts`. Запустить пять тестов: tiktok_http_regressions.js, tiktok_post_evidence_regressions.js, tiktok_schedule_regressions.js, tiktok_staging_regressions.js, tiktok_caption_regressions.js из tests через node. Любой ненулевой код — остановка сборки. Schedule JS-тест пока модельный; он не доказывает исполнение C#-генератора.
7. `dotnet build VideoBatch.csproj -c Release -p:ApplicationIcon=`. Этот параметр нужен, если app.ico отсутствует. Проверить сборку на Windows. Локальный анализ в Linux не заменяет её.
8. Подготовить отдельный комплект: новый EXE и весь совместимый tools/uploader, включая tiktok-aws-sigv4.js, node.exe и установленный playwright-core. Не обновлять один worker при старом EXE. Сверить SHA256 исходных файлов и файлов комплекта. Настройки пользователя не заменять шаблоном.
9. При пустой/неработающей кнопке сверки проверить, что запускается новый EXE, а не старый ярлык. Убедиться, что новые поля переживают сохранение/перезапуск на копии settings.xml.

## Контрольный тест (выполняет пользователь на ПК)

1. Один профиль, один новый ролик с узнаваемой подписью. Проверить аккаунт Studio. Записать LocalJobId, Profile ID и ожидаемое местное время. Не запускать одновременно старое приложение.
2. Запустить HTTP, проверить строку сборки v5.4-evidence, оба IP, стадии apply/project/upload/commit/post. Если маршрут не совпал — не отключать проверку: исследовать настройки request-транспорта и Dolphin.
3. Открыть Studio того же TikTok-аккаунта. Проверить черновики, запланированные и ролики на проверке. Сопоставить ролик, подпись, время и ссылку/ID публикации. Upload videoId и projectId не равны доказательству публичного поста.
4. При успехе только post, но отсутствии ролика: сохранить JSONL этой попытки. Не отправлять ещё четыре ролика и не сбрасывать защиту от повторов.
5. Для установления причины нужен обезличенный ответ именно post этой попытки: HTTP status, status_code, status_msg, список имён полей ответа и коды single_post_resp_list. Полный HAR/cookies/Authorization/msToken/accessKey/secretKey передавать в чат и репозиторий нельзя.
6. Если понадобится сравнение с ручной загрузкой: локально записать один ручной успешный сценарий того же аккаунта. Сравнивать последовательность запросов, структуру payload и имена полей, признаки подтверждения и schedule_time. Не копировать токены из чужих проектов; не подбирать регион перебором. Сетевой захват с секретами хранить только локально.
7. Только после подтверждения первого ролика проверить два с интервалом 10–30 минут. В Studio сверить фактические времена; убедиться, что сервер не округлил или проигнорировал секунды. Затем пачка пять. Не называть тест пройденным только по строке done.

## Обязательные дополнительные проверки агента

- Отмена после commit/post: нет автоматической повторной публикации при новом запуске.
- Частичная пачка: принятые не отправляются повторно, неизвестный элемент блокирует дальнейший запуск, оставшиеся не помечены опубликованными.
- Нет изменения YouTube-очереди, профилей, подписей и путей пользователя после миграции.
- Сохранение расписания/перезапуск на ПК, часовой пояс ПК и точность до секунды. Текущий генератор использует локальный DateTime: отдельно проверить переход DST, если он применим; для Красноярска такой переход не нужен.
- Ошибка записи settings.xml должна останавливать HTTP-runner, а не считаться «плохой JSON-строкой».

Отчёт: исходный локальный SHA; integration SHA; список сохранённых местных изменений; коды завершения тестов/сборки; путь готового комплекта; результаты живого теста отдельно. При недоказанном результате писать «не подтверждено», не «работает на 100%».
