Репозиторий Egorka-777/myvideopril, ветка feat/assembly-speed-20261009.
Основа ветки — 0b047fb9c8042f41a0696c1142055ec3762ad85d, последняя доработка своих/общих видео сцен и удаления сцен. Новые коммиты после этой основы — ускорение. Раздел аккаунтов находится в другой ветке; при переносе сохраняй его и все другие установленные функции.

## Что уже сделано

AssemblyEngine.Render теперь вызывает AssemblyRender.Run: один FFmpeg-процесс собирает видеофоны, изображения, переходы и музыку сразу в итоговый MP4. Промежуточные scene-N.mp4 в обычной сборке не создаются. PNG читается одним кадром, overlay удерживает его до конца соответствующей сцены. Изображения сначала накладываются на сцену, потом вся сцена с ними участвует в переходе. Положение, размер, прозрачность и интервалы появления остаются из шаблона. Одинаковые растры повторно используются только в пределах текущего запуска; ключ включает источник, хеш, размер холста и все параметры рисования. Временный кэш удаляется при завершении/отмене.

Автоматический режим пробует настоящий короткий H.264 encode в выбранном разрешении через h264_nvenc, h264_qsv, h264_amf. Одного наличия имени в `ffmpeg -encoders` недостаточно. Если драйвер/оборудование/параметры не подходят, используется libx264. При ошибке аппаратного кодирования самого ролика выполняется одна повторная попытка на CPU; следующий ролик в пачке сразу идёт на CPU. Проверки наличия GPU выполняются один раз на запуск пачки. Отмена не запускает повторную попытку.

CPU: veryfast / CRF 20, кодировщик до 8 потоков, граф фильтров до 4, декодер каждого входа 1. Границы зависят от Environment.ProcessorCount. Разрешение и FPS не понижаются автоматически. Пресет сжимает менее эффективно, поэтому файл может быть больше, чем при прежнем fast. GPU-параметры качества не являются точным эквивалентом CRF.

В меню формата добавлено «Ускорение · авто/процессор» с аккуратным выбором «Автоматически» / «На процессоре». Это сохраняется в RenderMode. Старые шаблоны без поля получают auto. Индикатор теперь показывает ход кодирования текущего ролика. Рядом с готовым MP4 записывается .performance.xml с выбранным кодировщиком, числом попыток, временем подготовки, проверки GPU, кодирования и проверки результата. Эти отчёты не требуют ручного заполнения.

Ролики продолжают собираться последовательно: не запускай 21 FFmpeg одновременно. Это сохраняет контролируемую нагрузку и единый порядок фиксации комбинаций. История и сигнатуры обновляются только после успешного рендера/проверки. Старый RenderLegacy оставлен только для сравнения в тестах; UI его не вызывает.

## Установка на ПК

1. Найди реально запускаемый EXE, его исходники, текущую ветку и локальные изменения. Закрой приложение. Сохрани копию исполняемой папки, действующих settings.xml, шаблонов, истории комбинаций, accounts.vault с bak, профилей и материалов. Не отправляй реальные данные в Git.
2. `git fetch origin feat/assembly-speed-20261009`. Посмотри весь диапазон `git log --reverse --oneline 0b047fb9c8042f41a0696c1142055ec3762ad85d..origin/feat/assembly-speed-20261009`. Если доработка сцен уже установлена, перенеси этот диапазон через `git cherry-pick 0b047fb9c8042f41a0696c1142055ec3762ad85d..origin/feat/assembly-speed-20261009` в рабочую ветку. Если основа ещё не установлена, сначала сопоставь/перенеси изменения сцен; не заменяй текущую рабочую версию EXE, собранным от старой main. Не выбирай только последний коммит ветки.
3. При конфликтах сохраняй изменения аккаунтов, маршрутизации видео по сценам, объектов, переходов и истории. В csproj добавь AssemblyRender.cs; существующие Compile Include, особенно AssemblyInventory.cs и AccountLibrary*.cs, должны остаться.
4. `dotnet build VideoBatch.csproj -c Release -p:ApplicationIcon=`. Затем `dotnet build tests/AssemblyHost/AssemblyHost.csproj -c Release`. Обнови фактически запускаемый EXE/config, сохраняя tools и пользовательские файлы. Зафиксируй установленный коммит и полный путь EXE.

## Проверка, которую нельзя пропустить

5. Выполни Windows UI/планировочные проверки из `.github/workflows/video-assembly.yml`, затем `python tests/assembly_integration.py --host tests/AssemblyHost/bin/Release/net8.0-windows/AssemblyHost.dll`. Они проверяют настоящий MP4, фиксированную карточку, смену объектов, тайминг, свои видео сцен, переход всех слоёв вместе, непрерывную музыку и отмену. Проверь также ранее установленные аккаунты/обработку; их изменения не должны потеряться.
6. `python tests/assembly_speed.py --host tests/AssemblyHost/bin/Release/net8.0-windows/AssemblyHost.dll`. Сравнение использует один и тот же план и три повтора каждого пути, чередуя порядок. Проверяются SSIM декодированных роликов, повторное использование растров, намеренная ошибка кодировщика с возвратом на CPU и отмена уже начатого кодирования. Это синтетические данные, не настройки пользователя.
7. На пользовательском ПК отдельно запиши модель CPU/GPU, ОЗУ, версию запускаемого FFmpeg и режим питания. Проверь auto и cpu на копии одного реального шаблона. Сравни одинаковые исходники, позиции, длительность, переход, разрешение и FPS, без одновременных сборок. Для старого/нового пути используй режим benchmark тестового хоста; историю/материалы пользователя не расходуй. Если шаблону не хватает уникальных картинок для одного плана, не сбрасывай историю: используй копию набора.
8. Посмотри глазами начало, каждую границу сцен и последнюю карточку, читаемость текста/картинок; прослушай музыку. В auto проверь фактический Encoder в .performance.xml. Наличие видеокарты само по себе не доказывает, что аппаратный кодировщик заработал. Успешный аппаратный путь требует проверки именно на этом оборудовании; CI без подходящей GPU подтверждает CPU и резервный путь.
9. Пачку из 21 ролика проверь на копии материалов и шаблона. Посчитай готовые MP4, XML-рецепты и записи истории; если комбинаций меньше 21, приложение должно сообщить настоящий лимит. Не выдумывай недостающие связки и не сбрасывай историю для демонстрации числа. Проверь «Стоп» во время кодирования: готовые ролики остаются, текущая комбинация не расходуется, временный каталог удаляется.
10. Отчёт пользователю: установленный коммит, запускаемый EXE, фактический кодировщик, одинаковые настройки сравнения, медиана времени до/после, время пачки и результат проверки картинки/музыки. Если авто не смог использовать GPU, покажи это фактом. Не обещай скорость другого компьютера по результатам CI. Если длинный переход остаётся основным расходом, приведи EncodeSeconds и сравнение одного реального плана; не заменяй выбранный эффект обычной склейкой и не снижай размер кадра скрытно.
