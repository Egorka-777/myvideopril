# Studio v20: новая вкладка для следующего видео

Ветка `fix/studio-upload-recovery-20261022`, база main `2207c946c7f85b7b9363f5641be84a223a6aba47` (v19h). BUILD в обоих JS: **`2026-10-22-studio-upload-recovery-v20`**. Эта инструкция имеет приоритет над описанием v19 в предыдущих handoff/Shorts-документах.

## Поведение

Один файл → заголовок → всё SEO-описание → реклама/ИИ No → передача завершена → Public → одно основное Publish → при наличии предупреждения о продолжающейся проверке одно подтверждение в нём → экран завершения Studio → результат сохранён в приложении → **следующий файл в новой вкладке**.

Обычная успешная публикация больше не открывает вторую вкладку для обязательной сверки редактора по ID и не ждёт активной нижней кнопки Close. Новая вкладка служит именно следующей загрузке. Предыдущая вкладка, созданная заданием, закрывается только после подтверждения публикации. Вкладки, открытые пользователем, сохраняются. Последний экран остаётся доступен. Shorts по-прежнему без превью; длинные видео сохраняют превью и расписание.

ID — внутренняя ссылка для восстановления после сбоя, а не дополнительное препятствие обычной публикации. Если Studio не показал однозначное завершение, сохраняется проверка существующего видео, без повторного Publish/передачи. Предупреждение «проверка видео ещё продолжается» само по себе ещё не является завершением публикации.

## Что исправлено и что известно

- v19h ошибочно считал обёртку мастера и вложенное предупреждение разными диалогами. Выбирается внутреннее видимое окно; вторичное подтверждение нажимается максимум один раз за ожидание, вне короткой проверки состояния страницы.
- Прежний worker создавал новую страницу до поиска старого черновика. Теперь ищется существующая вкладка по точному ID или точному заголовку/имени исходника. Неоднозначный выбор не угадывается.
- ID сохраняется до длинного описания, как только появляется ссылка. Этапы `transferring → editing → publishing → confirmed` записываются EXE на диск **до ACK**. Возобновляемый черновик продолжает редактироваться, а не проверяется как уже публичный.
- Убран повтор передачи через CDP после неоднозначного таймаута обычной передачи. Старое pending не стирается лишь потому, что в новой вкладке нет мастера.
- Проверка полного описания сохранена. Если текст перестал меняться, нет повторного ожидания 35 секунд на каждом недостающем фрагменте: точный сырой префикс сохраняется, недостающий хвост вводится после восстановления фокуса. Посторонний текст не принимается. Политика конечна, ввод отменяется вместе с этапом.
- В полном журнале сохраняются все этапы, длительность, ACK, навигация, ошибки страницы и статусы сетевых ошибок. При сбое — JSON состояния и PNG экрана. Нет сетевых тел запросов, cookies/заголовков авторизации или чтения сессии. Скриншот может содержать видимые данные канала.
- Одно событие `start` на задание. Лог показывает путь uploader, Node, версию протокола EXE и BUILD. Установка пишет хеши полного комплекта; частичная/изменённая установка отклоняется до открытия профиля.

Скриншот с обрывом описания около 1080 символов не доказывает конкретную причину: возможны фокус, замена редактора или изменение текста Studio. Для точной причины нужен новый JSON/JSONL. В изолированном браузере тест намеренно теряет хвост на 1080 символах и доказывает его восстановление без стирания уже правильного префикса.

## Установка агентом на ПК

**Нужен весь новый EXE + JS вместе**: в v20 изменился протокол долговременного сохранения. Не копировать одни JS по старой инструкции v19f. Настройки/аккаунты/прокси/банки/видео не удалять и заново не импортировать.

1. Скачать артефакт **VideoBatch-Studio-v20-Update** из зелёного Actions этой ветки. Распаковать в отдельную папку. Сверить `SOURCE_COMMIT.txt` с коммитом успешного прогона.
2. Остановить задачи и закрыть VideoBatch. Dolphin и пользовательские вкладки принудительно не закрывать.
3. Из распакованного обновления выполнить:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Sync-StudioUploader.ps1 -KitRoot D:\VideoBatch\VideoBatch -WhatIf
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Sync-StudioUploader.ps1 -KitRoot D:\VideoBatch\VideoBatch
```

Скрипт проверяет EXE protocol 2, синтаксис JS, работающие процессы, резервирует заменяемые файлы, копирует весь код и проверяет SHA256. При ошибке копирования восстанавливает прежние файлы. `node.exe`, `node_modules`, пользовательские настройки и материалы сохраняются. Запускать из отдельной папки, не поверх той же папки-источника. Из исходников сначала собрать `dotnet build VideoBatch.csproj -c Release -p:ApplicationIcon=`; скрипт найдёт EXE в `bin/Release/net48`.

4. Запустить именно `D:\VideoBatch\VideoBatch\VideoBatch.exe`. В начале лога должны быть BUILD **v20**, EXE protocol **2**, фактические пути нового комплекта.

В разработке нет доступа к диску D:, Dolphin и реальным аккаунтам пользователя. CI использует изолированные браузерные страницы; статус живого прогона **NOT_RUN**. Не объявлять загрузку в аккаунты проверенной по одному зелёному CI.

- Два профиля с действующим входом Google, максимум два параллельных задания на время проверки.
- По три Shorts подряд на профиль, описания из текущей базы около 1650 символов. Разрешён один и тот же тестовый исходник в разных новых заданиях; запрета по хешу исходного файла нет.
- В каждом канале: три строки полного описания с длиной/SHA256, три основных Publish, три `item_confirmed`, две `studio_new_tab`, `done`. Не должно быть обязательного `studio_verify` или ожидания Close на нормальном пути.
- Проверить созданные видео в Studio. Сохранить время начала с часовым поясом и профиль каждого задания.

Офлайн-аудит стандартного свежего прогона (не восстановление старой частично выполненной очереди):

```powershell
& D:\VideoBatch\VideoBatch\tools\uploader\node.exe D:\VideoBatch\VideoBatch\tools\uploader\studio-run-audit.js --log "$env:LOCALAPPDATA\VideoBatchDesktop\diagnostics\app-YYYYMMDD.jsonl" --since "2026-10-22T15:00:00+07:00" --profiles "PROFILE1,PROFILE2" --out .\studio-audit.json
```

Подставить настоящий файл/начало прогона/ID. `PASS_LOG_CONTRACT` подтверждает структуру переданного лога, а не независимую сетевую проверку канала.

## Если появилась ошибка

Не увеличивать все таймауты, не стирать pending и не запускать повторный Publish наугад. Сначала собрать всё одной командой:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File D:\VideoBatch\VideoBatch\scripts\Collect-StudioDiagnostics.ps1 -KitRoot D:\VideoBatch\VideoBatch
```

На рабочем столе появится ZIP за последние 24 часа: `youtube-*.log`, `diagnostics/app-*.jsonl`, `studio-trace-*.jsonl`, `youtube-studio-*.json/png`, manifest и хеши установленных файлов. Settings, токены, сессии и исходные видео туда не копируются. Архив никуда автоматически не отправляется. Перед передачей учесть видимые на PNG данные канала.

Порядок разбора: `studio_runtime`/manifest → последний этап и его время → `editorFailure.comparison` (длины, первый разный символ, SHA256), фокус и blocker → предупреждение/экран завершения → `durable_begin/ack`. Полный JSON пишется даже если часть DOM не отвечает; `captureErrors` указывает, чего получить не удалось.

Если историческая отправка pending без ID и нужной открытой вкладки: в том же Dolphin-профиле открыть **Studio → Контент → соответствующий черновик**, затем повторить задачу приложения. Программа подхватит его ссылку. Если такого черновика нет, сначала вручную установить, был ли файл принят; автоматического удаления/сброса неизвестного видео нет.
